# locqa: контроль качества локализации ARB

CLI-инструмент для кейса 02 «Qazaq Loc QA» (Grand Mobile × Decentrathon 6.0). Он находит ошибки в любых Flutter ARB-файлах, а для казахского и узбекского у него есть отдельные языковые правила. Инструмент выдаёт `report.json` и HTML-отчёт, готовит таблицу для носителя языка и собирает `intl_kk_fixed.arb` только из строк, которые проверил человек.

Зависимостей нет, только стандартная библиотека Python ≥ 3.10.

```bash
pip install -e .            # или: python -m locqa ...
locqa check --source intl_ru.arb --target intl_kk.arb --glossary glossary.csv --out report.json
```

## Рабочий цикл на хакатоне

```bash
# 1. Найти проблемы. Файлы других языков помогают ловить wrong_language.
locqa check --source intl_ru.arb --target intl_kk.arb --glossary glossary.csv \
  --ref intl_uz.arb --ref intl_en.arb --out report.json        # + report.html

# 2. Собрать кандидатов в глоссарий из самих файлов. Носитель проверяет их и переносит в glossary.csv.
locqa mine-terms --source intl_ru.arb --target intl_kk.arb --out terms.csv

# 3. Подготовить таблицу для носителя: одна строка на ключ, сортировка по severity и confidence.
locqa export-review --report report.json --out review.csv
#    Носитель заполняет decision (accept | edit | keep | skip), final_text и reviewer.

# 4. Собрать исправленный файл. Применяются только строки с решением и именем проверяющего.
locqa apply --target intl_kk.arb --review review.csv --source intl_ru.arb --out intl_kk_fixed.arb

# 5. Проверить результат: сначала locqa, затем настоящий flutter gen-l10n.
locqa validate intl_kk_fixed.arb --source intl_ru.arb
bash scripts/check_gen_l10n.sh ./l10n intl_ru.arb     # нужен Flutter SDK

# 6. Финальный отчёт: reviewed_by_human, находки, отклонённые носителем (keep), убираются,
#    ошибки, найденные при ревью, добавляются в report.json (summary.review)
locqa check ... --review review.csv --out report.json
```

## Команды

| Команда | Что делает |
|---|---|
| `check` | Все проверки, `report.json` + HTML. Опции: `--ref` (повторяемая), `--allow`, `--vocab`, `--min-confidence` (0.5), `--all`, `--only`, `--flat`, `--translit`, `--review`, `--fail-on`, `--llm …` |
| `validate` | Пре-флайт перед `flutter gen-l10n`: JSON, дубликаты ключей, ICU, `other` в plural/select, совпадение плейсхолдеров с исходником, `@@locale` против имени файла, имена ключей шаблона (gen-l10n требует валидные Dart-геттеры `[a-z$][A-Za-z0-9_$]*`, правило перенесено из `_isValidGetterAndMethodName`) |
| `export-review` / `apply` | Цикл ревью носителем, подробнее ниже. `--suggestions` подмешивает в таблицу предложения LLM или коллеги; `apply --include-unreviewed` собирает черновик с `x-reviewed: false` |
| `review-stats` | Цифры для методологии: сколько строк проверено, сколько изменено, precision по типам |
| `mine-terms` | Пары «русская основа → устойчивый перевод» с покрытием и ключами-исключениями |
| `seed` / `eval` | Самопроверка: подложить синтетические ошибки и посчитать recall по типам |
| `translit` | Казахская кириллица → латиница. Меняется только литеральный текст, ICU-разметка не трогается |

Коды выхода: `0` — успешно; `1` — сработал `--fail-on`, ошибка `validate` или `apply --strict`; `2` — ошибка ввода (файл, JSON).

## Методология

### Принцип: детерминированные правила, затем статистика, затем LLM, затем человек

1. **Детерминированные правила** покрывают случаи с почти нулевой ошибкой: отсутствующие ключи, ICU-синтаксис, набор плейсхолдеров, аффикс сразу после плейсхолдера, смешение кириллицы и латиницы в одном слове, буквы, которых нет в алфавите.
2. **Статистика по самому файлу.** Медианное отношение длин kk/ru, частоты слов (чтобы заметить «кате» при 40 вхождениях «қате»), устойчивые переводы терминов.
3. **LLM (опционально, `--llm`)** проверяет то, что эвристикам не по силам: кальки и неестественный порядок слов. Модель только добавляет находки, сама она файл не правит.
4. **Человек.** В исправленный файл попадает только то, что носитель принял или отредактировал.

Перевод заново всего файла через LLM сознательно не используется: по брифу непроверенные массовые замены снижают оценку.

### Как определяется каждый тип

| Тип | Правило | Severity / confidence |
|---|---|---|
| `untranslated` | Ключа нет, значение пустое или не строка | high / 0.99 |
| `same_as_source` | Совпадает с исходником после нормализации пробелов и регистра. Исключения: строки без букв (числа, плейсхолдеры), только латиница (бренды), слова из глоссария с `kk == ru` или `type=brand`, список казахских заимствований (`KK_LOANS`), `--allow` | 2+ кириллических слова — high / 0.9; одно слово — medium / 0.6 (часто легитимное заимствование) |
| `placeholder_mismatch` | Разные множества имён аргументов (с учётом вложенности) или ICU не разбирается; плюс printf-плейсхолдеры `%s`/`%d`. Автоисправления: переименование, если одно имя пропало и одно добавилось; кириллица в имени (`{nаme}`); имя без скобок (`Жаңарады: time` → `{time}`) | high / 0.95–0.98 |
| `plural_mismatch` | Нет `other`, недопустимые селекторы, plural превратился в простой плейсхолдер, не хватает CLDR-форм целевой локали (kk: one/other) или есть лишние (few/many в kk). Поддерживаются select и selectordinal | high / medium / low по последствиям |
| `glossary_violation` | Русский термин найден (стемминг или `ru_regex`), а в переводе нет ни канонической формы, ни допустимого варианта. Казахская форма ищется по префиксу с учётом озвончения п/қ/к; для форм из `kk_forbidden` даётся исправление | Бренды high / 0.85; термины medium / 0.65; −0.1 для записей со статусом `draft` |
| `length_overflow` | Тип элемента выводится из имени ключа (`button`, `tab`, `title`…; глаголы `buy`, `cancel` считаются только без маркеров сообщения `success`, `error`…) или из `description`. Ожидаемая длина равна длине исходника × медиане kk/ru по коротким строкам файла. Порог: кнопки ×2.0 (не меньше длины исходника + 10), заголовки ×2.2 (+12), прочие короткие строки без точки на конце ×2.5 (+15). Дополнительно для строк ≤ 20 символов, которые основное правило пропускает (части фраз `*Prefix/*End`, ярлыки с «:»): рост ≥ ×3.5 и ≥ +18 символов; у частей фраз — только если текст продолжается после завершающего знака исходника. Плейсхолдер считается за 6 символов. С `--translit` учитывается и длина латиницы | Кнопки high/medium / 0.85, заголовки medium/low / 0.75, прочие medium / 0.7 при превышении ×3, иначе low / 0.55 |
| `machine_translation_suspect` (смысл) | Проверка `adequacy`: по всему файлу считаются ассоциации слов ru↔kk (коэффициент Dice, leave-one-out). Если казахское слово в остальных строках переводит другое русское слово и не связано ни с одним словом исходника, строка подозрительна | medium / 0.45 — лид для ревью, ниже порога по умолчанию |
| `machine_translation_suspect` (ложные друзья) | Список `MT_FALSE_FRIENDS`: в исходнике русское многозначное слово, в переводе — его неигровое словарное значение: ставка → «тігіс» (шов), кейс → «іс» (дело), инвентарь → «түгендеу», персонаж → «таңба» (символ), разрешение → «шешім», отменить → «болдыру», зелья → «жер», фары → «бағдаршам». Казахское слово без русского триггера не помечается | medium / 0.8; «тігіс» 0.6 (в разделе это системный выбор) |
| `machine_translation_suspect` | В казахском тексте (есть казахские буквы или частые казахские слова файла) встречаются русские служебные слова («и», «для», «что»…) или русские словоформы (‑ться, ‑ение, ‑ный, ‑ено…). Список калек с низкой уверенностью. Основной инструмент для этого типа — LLM | medium / 0.7–0.75; кальки low / 0.45 (ниже порога по умолчанию) |
| `inconsistent_term` | Для русских основ, встречающихся в 6+ ключах, ищется перевод, который сопровождает основу в ≥ 85 % ключей и редко встречается без неё. Помечаются ключи без него — только существительные, не более 2 исключений на термин, короткие строки (≤ 8 слов). Термины из глоссария исключены, ими занимается `glossary_violation`. (`mine-terms` по умолчанию: 4+ ключа, ≥ 75 %) | medium / 0.2 + 0.5 × покрытие |
| `suffix_harmony` | Плейсхолдер или `#`, за которым сразу (с дефисом или без) идёт падежный, порядковый или множественный аффикс. Запись «{n}-орын», «{n}-күн» (число, дефис, существительное) — норма казахского и не помечается | high / 0.9–0.95 |
| `orthography` | (1) Кириллица и латиница в одном слове, исправление гомоглифов. (2) Слово с русской буквой вместо казахской: вариант с ә/ғ/қ/ң/ө/ұ/ү/һ/і встречается в файле или словаре `--vocab` минимум в 3 раза чаще. (3) uz: oʻ/gʻ записаны не через U+02BB, хотя файл в ≥ 80 % случаев использует ʻ. (4) Двойной пробел или пробел перед знаком препинания, которых нет в исходнике. (5) Повтор слова | medium/low / 0.6–0.95 |
| `wrong_language` | Перевод дословно совпадает со строкой из `--ref`-файла другого языка (0.97). Маркеры: ў/ҳ — узбекская кириллица; латиница с oʻ/gʻ или узбекскими словами; английские служебные слова; русские служебные слова без признаков казахского. Для латинских локалей — несовпадение письменности | high/medium / 0.55–0.97 |

**Severity** описывает последствия для игрока: high — падение сборки, сломанный UI, текст не на том языке; medium — заметная ошибка; low — косметика. **Confidence** — оценка правила, насколько находка верна. По умолчанию в отчёт попадают находки с confidence ≥ 0.5, остальные учитываются в `summary.suppressed_below_threshold` и показываются с `--all`. Порог выбран из-за метрики precision: жюри проверяет 100 случайных находок, поэтому шум стоит дороже, чем пропуск слабых подозрений.

### Аффиксы после плейсхолдера (обязательная часть и бонус)

`{name}-ға` правильно только для части имён: окончание зависит от последнего звука значения, которое подставляется в рантайме. Инструмент:
- помечает такие строки как `suffix_harmony` / high и указывает падеж с полным набором вариантов окончания;
- **автоматически предлагает переформулировку** для плейсхолдеров-людей (`name`, `nick`, `player`, `sender`…). Аффикс переносится на слово-буфер с фиксированной гармонией: `{name}-ға ақша жіберу` → `{name} ойыншысына ақша жіберу`. Падежи: ‑на, ‑ның, ‑н, ‑нда, ‑нан, ‑мен. Если слово «ойыншы» уже стоит перед плейсхолдером, оно не дублируется;
- для числовых плейсхолдеров (`count`, `amount`…), `#` и случаев, когда безопасной замены нет, ставит тег `needs_code_handling` в соответствии с брифом.

Предложение — только черновик для носителя. В файл оно попадает лишь после `accept`.

### Ревью носителем и флаг проверки

В `review.csv` на каждый ключ одна строка со всеми находками. Значения `decision`:
- `accept` — применить `suggestion`;
- `edit` — применить `final_text`;
- `keep` — строка верна, находка ложная (используется для оценки precision);
- `skip` или пусто — не проверено.

`apply`:
- правит файл текстово: порядок ключей, отступы, повторяющиеся `@@comment` и все вхождения дублирующегося ключа сохраняются, неизменённые строки остаются байт-в-байт;
- применяет строку, только если указан `reviewer`;
- отклоняет текст, который ломает ICU или меняет набор плейсхолдеров относительно исходника;
- у каждого изменённого ключа записывает метаданные:

```json
"send_money_to": "{name} ойыншысына ақша жіберу",
"@send_money_to": {"x-reviewed": true, "x-reviewed-by": "Айгерім", "x-original": "{name}-ға ақша жіберу", "x-issues": ["suffix_harmony"]}
```

- кладёт рядом `intl_kk_fixed.review.json` со списком изменений (`reviewed_by_human: true`), строк `keep` и отклонённых строк.

Без отметки человека ни одна строка не меняется. Исключение — черновик `apply --include-unreviewed`: туда попадают и предложения без решения, с `"x-reviewed": false`. Такой файл подходит для просмотра носителем, но не для сдачи: строки без проверки в оценку качества не идут.

### Формат report.json

Объект с полями `tool`, `version`, `source`, `target`, `summary`, `llm`, `findings[]` и `diagnostics[]`. Каждая находка соответствует схеме из брифа (`key`, `issue_type`, `severity`, `source`, `target`, `evidence`, `suggestion`, `confidence`, `reviewed_by_human`), плюс два служебных поля: `rule` (сработавшее правило) и опциональный `tags`. На каждую пару (ключ, тип) приходится одна находка. Если нужен голый массив находок, используйте `--flat`. Проблемы уровня файла — дубликаты ключей, лишние ключи, метаданные без ключа, расхождение `@@locale` с именем файла — вынесены в `diagnostics`, чтобы не портить precision по 11 типам.

### LLM и стоимость

```bash
export LOCQA_LLM_API_KEY=... LOCQA_LLM_MODEL=<id модели>
export LOCQA_LLM_PRICE_IN=<$ за 1M входных токенов> LOCQA_LLM_PRICE_OUT=<$ за 1M выходных>
locqa check ... --llm anthropic --llm-scope flagged --llm-dry-run   # только оценка объёма
locqa check ... --llm anthropic --llm-scope flagged                 # или --llm openai (любой OpenAI-совместимый endpoint, LOCQA_LLM_BASE_URL)
```

- `flagged` отправляет только ключи с эвристическими находками, `all` — все переведённые ключи. Батчи по 20 строк, с глоссарием и английской версией (если передана через `--ref`).
- Ответы кэшируются в `.locqa_llm_cache.json`, поэтому повторный прогон бесплатен.
- Confidence находок от LLM ограничен значением 0.8. Предложения, которые ломают плейсхолдеры, отбрасываются.
- Расход фиксируется в `report.json → llm`: `input_tokens`, `output_tokens`, `cost_usd = (in × price_in + out × price_out) / 10⁶`. Эту цифру нужно перенести в отчёт для жюри.
- `--llm-dry-run` грубо оценивает объём (≈ 2.5 символа на токен для кириллического JSON) до трат.

### Самопроверка без ключа ответов

```bash
locqa seed --source intl_ru.arb --target intl_kk.arb --glossary glossary.csv --ref intl_uz.arb --ref intl_en.arb \
  --n 100 --out seeded_kk.arb --answers answers.json
locqa check --source intl_ru.arb --target seeded_kk.arb --glossary glossary.csv --ref intl_uz.arb --ref intl_en.arb --out seeded.json
locqa eval --report seeded.json --answers answers.json
```

Подкладываются 9 типов: `inconsistent_term` и `plural_mismatch` без безопасного синтетического рецепта не подкладываются. **Это оптимистичная оценка**: синтетические ошибки повторяют наше представление о каждом типе, а не то, как ошибки подложили организаторы. Для честного precision используйте решения `keep` из ревью: precision ≈ 1 − keep / (accept + edit + keep) по проверенным находкам.

## Глоссарий

`glossary.csv` содержит колонки `ru, kk, en, note, kk_variants, kk_forbidden, ru_regex, type, status`. Обязательные из них — `ru` и `kk`. Для другой локали вместо `kk` используется колонка с её кодом (`uz`, `uz_variants`…).

Статусы записей:
- `observed` — так переводит большинство строк файла Grand Mobile, покрытие указано в `note`;
- `from_brief` — правило из брифа (бренды не переводятся);
- `draft` — нужно решение носителя.

Сленг игроков (варн, мут, фура, ГК) описан в `note` и в `kk_variants`, где это допустимо в UI. Записи `observed` отражают фактическое употребление, носитель их не проверял.

## Бонусы

- **Узбекский:** `locqa check --source intl_ru.arb --target intl_uz.arb --ref intl_kk.arb ...`. Языконезависимые проверки, письменность, апострофы oʻ/gʻ, маркеры других языков. Казахские правила (аффиксы, ә/ғ/қ) для uz не запускаются.
- **Транслитерация:** `locqa translit` и `check --translit`. Таблица в `locqa/translit.py` составлена по проекту алфавита 2021 года **по нашему пониманию; с нормативным текстом она не сверялась**. Свою таблицу можно передать через `--table`.
- **GitHub Action:** `.github/workflows/locqa.yml` запускает `validate` и `check --fail-on high` на каждый PR с изменениями `*.arb` и отдельным job прогоняет `flutter gen-l10n` через `scripts/check_gen_l10n.sh`. Пути `ARB_DIR` и `TEMPLATE` настраиваются в начале файла. В шаблоне Grand Mobile есть ключи `UNeedHelp`, `TowConfirmDesc`, `inventoryEquipped@description`, на которых gen-l10n падает ещё до переводов; поэтому job запускается с `DROP_INVALID_TEMPLATE_KEYS=1` — скрипт убирает такие ключи из временных копий (оригиналы не трогаются) и печатает их список. После исправления шаблона флаг нужно выключить.
- **Автопереформулировка аффиксов:** описана выше.

## Тесты

```bash
pip install -e '.[test]' && pytest
```

Тесты используют синтетический корпус из `tests/conftest.py`, данных партнёра в них нет.

Что покрыто тестами:
- ICU-парсер;
- ввод-вывод ARB;
- каждый тип находки, включая отрицательные случаи (бренды, числа, заимствования);
- полный цикл `check → export-review → apply → validate`;
- `seed`/`eval`;
- LLM-клиент на фейковом транспорте (кэш, стоимость, отбрасывание сломанных предложений);
- транслитерация.

Отдельный тест требует ноль находок на чистом корпусе.

## Ограничения и открытые вопросы

- `flutter gen-l10n` в этом репозитории не запускался: Flutter SDK нет в окружении разработки. `validate` — приближение, решает CI-job `gen-l10n`. По исходникам gen-l10n (`gen_l10n_types.dart`): у не-template файлов из `@key` читается только `placeholders`, поля `x-*` игнорируются; ошибка парсинга сообщения в любой локали валит генерацию; имена ключей шаблона проверяются до переводов.
- Шаблон `intl_ru.arb` из выдачи в текущем виде не проходит gen-l10n (3 ключа с недопустимыми именами, см. выше). Это проблема исходника партнёра, не перевода.
- `inconsistent_term` и частотная орфография зависят от размера и качества самого файла: на редких словах без `--vocab` они молчат.
- `machine_translation_suspect` без LLM ловит только грубые случаи (русские слова и формы внутри казахского текста).
- Вопросы организаторам (влияют на настройки): как матчится находка для recall — по ключу и типу или только по ключу; какой формат флага ревью ожидается; есть ли валидационная выборка с размеченными ошибками; какие эталонные казахские формы у пяти терминов глоссария; какой графикой написан узбекский файл.

## Данные

Данные партнёра нельзя коммитить: `.gitignore` исключает `*.arb`, `review*.csv`, отчёты и LLM-кэш. Удалите данные в течение 14 дней после объявления победителей. Если `--llm` отправляет строки во внешний API, это разрешено брифом, но такие запуски стоит перечислить в методологии.
